# SSR mode

<p class="lede">The <code>@sigx/vite</code> plugin has an SSR mode that produces both halves of a server-rendered app — the client bundle and the server bundle — from a single <code>vite build</code>, and a dev-server handler that shares one module graph with your app.</p>

This is the build-and-dev side of SSR; the runtime APIs it feeds live in [`@sigx/server-renderer`](/server/packages/server-renderer/overview).

## Turning on SSR

Pass an `ssr` block to the plugin, pointing at your server entry:

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import { sigx } from '@sigx/vite';

export default defineConfig({
    plugins: [
        sigx({
            ssr: { entry: 'src/entry-server.tsx' },
        }),
    ],
});
```

| Option | Default | Meaning |
|---|---|---|
| `entry` | — (required) | Your server entry module. |
| `clientOutDir` | `'dist/client'` | Where the browser bundle + manifest are written. |
| `serverOutDir` | `'dist/server'` | Where the server bundle is written. |
| `adapter` | `nodeAdapter()` | The [deployment adapter](/vite/docs/deploy-adapters) shaping the server build — externalized Node output by default; Cloudflare/Vercel/Netlify adapters produce bundled platform builds. |

One `vite build` now runs both environments (via Vite's builder API): the client build emits `.vite/manifest.json` alongside the browser assets, and the server build emits `entry-server.js`.

With the default adapter the server bundle **externalizes its dependencies** rather than bundling a second copy of the runtime. That matters for correctness, not just size: a bundled runtime carries its own DI token identities and would never see the app's provides. (In practice the spa-ssr server bundle drops from ~97 kB to ~25 kB.) Edge platforms can't resolve `node_modules` at runtime, which is why their [deploy adapters](/vite/docs/deploy-adapters) switch to a **total** bundle — everything in one module graph preserves the same DI invariant from the other direction.

## The islands transform

If you use islands, add `sigxIslands()` from the `@sigx/vite/islands` entry:

```ts
import { sigx } from '@sigx/vite';
import { sigxIslands } from '@sigx/vite/islands';

export default defineConfig({
    plugins: [
        sigx({ ssr: { entry: 'src/entry-server.tsx' } }),
        sigxIslands(),
    ],
});
```

```ts
interface SigxIslandsOptions {
    include?: string | string[];   // default: *.island.ts(x), islands/**/*.ts(x)
    exclude?: string | string[];   // default: node_modules, dist
}
```

It does four things:

1. Stamps `__islandId` onto each island's named component export.
2. Rewrites signal declarations so island state gets a stable key (see [automatic state keys](/server/packages/ssr-islands/plugin-setup#automatic-state-keys)).
3. Serves `virtual:sigx-islands`, which registers a lazy `import()` per island.
4. Emits a `sigx-islands-manifest.json` on the client build (under `clientOutDir`, at `.vite/sigx-islands-manifest.json`), mapping island names → `{ chunkUrl, exportName }`. Feed that to `islandsPlugin({ manifest })`.

An island is a **named export** that is a component factory, in a file the `include` globs match. Names must be **unique across island files** — that name is the key.

## The dev-server handler

For `vite dev`, `@sigx/vite/ssr` gives you a request handler that renders through Vite's module runner — so the renderer, your app, and `islandsPlugin()` all share one module graph and one set of DI token identities:

```ts
import { createServer } from 'vite';
import { createDevRequestHandler } from '@sigx/vite/ssr';

const vite = await createServer({ server: { middlewareMode: true } });
const handler = await createDevRequestHandler(vite, {
    entry: '/src/entry-server.tsx',   // Vite-root-relative
    entryExport: 'createApp',         // default
});

app.use(vite.middlewares);
app.use(handler);
```

It fails fast at startup if `@sigx/server-renderer` isn't installed, and applies `ssrFixStacktrace` so errors point at your source.

### Styles in dev

The dev handler inlines the SSR module graph's CSS into the document `<head>`. There is nothing to configure.

This matters because of how Vite serves CSS in dev: a stylesheet reached through a JS import (`import './styles.css'` — so any app with Tailwind, daisyUI, CSS modules, or plain imported CSS) is served as a **JS module that injects a `<style>` at runtime**. Without inlining, dev SSR streamed a fully rendered document with no styles in the head, and the browser painted the entire page unstyled until the client entry executed.

The styles are emitted as `<style data-vite-dev-id="…">` — the shape Vite's client adopts on boot and HMR-replaces in place, so there are no duplicated rules and CSS HMR is untouched.

```ts
const handler = await createDevRequestHandler(vite, {
    entry: '/src/entry-server.tsx',
    devStyles: false,   // default: true
});
```

Set `devStyles: false` only when your template already ships a stylesheet link of its own.

This is **dev-only**. Production has always emitted the built manifest's real `<link>` tags via [`collectAssets`](/vite/docs/api), so it was never affected.

For **production**, the counterpart is `createRequestHandler` from `@sigx/server-renderer/node`, fed your built `entry-server.js` and manifest — see [Building a full SSR app](/server/packages/server-renderer/full-app).
