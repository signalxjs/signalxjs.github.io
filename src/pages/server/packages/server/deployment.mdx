# Deployment & security

A server function is served at `POST /_sigx/fn/<id>/<name>` — its stable key. You
wire that endpoint once per runtime; everything else — validation, error masking,
the security gate — is the same everywhere.

## One route per function, one version per deploy

Every function has **one** identity, the stable key `<id>/<name>`. It is the
route, the registry key and the [`useData(fn)`](/core/docs/data-loading#server-functions-as-keys)
data identity, and it is the same under every build role. A key's slashes are
real path separators, so the route reads as the id does and nothing in front of
the app has to preserve encoded slashes:

```
POST /_sigx/fn/@acme/api/src/cart.server.ts/addToCart
POST /_sigx/fn/cart/add/addToCart              # addToCart = serverFn({ id: 'cart/add', … })
```

Key seeds are package-qualified, so every app build of one solution mints the
identical key for a shared server module. Only a character a URL path genuinely
cannot carry is percent-encoded, per segment; a `..` segment in an id becomes
`_up`, and an explicit `id` that had to be rewritten warns at build time naming
the route it actually gets.

**Skew detection is a version tag, not a second route.** The build hashes each
function's normalized definition — a reformat or a comment keeps the hash, any
semantic change bumps it — bakes it into the stub, and the stub sends it with
every call: `"v"` in the POST envelope, `?v=` on a GET read. When it differs
from the registry's, the endpoint answers **`409`** with `code: 'version-skew'`,
and the stub throws the one hint a user can act on:

```
server function "addToCart" belongs to a different build than this page (version skew); reload to pick up the current one.
```

A `404` means only "unknown function". A call that carries no tag — curl, a form
post — is simply served, and so is every call through a hand-built `resolve`
table, which knows no version to compare against.

Moving or renaming a server module changes its key — a breaking API change for
a long-lived client, exactly like changing a REST route. Pin an explicit `id`
for published APIs; see [Native clients](/server/packages/server/native-clients#3-pin-the-routes).

## Development

Zero config. Add the `sigxServer()` plugin from `@sigx/vite/server` to your Vite
config and the dev server handles the endpoint from its middleware, loading the
real `*.server.ts` modules on demand:

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import sigx from '@sigx/vite';
import sigxServer from '@sigx/vite/server';

export default defineConfig({
  plugins: [sigx(), sigxServer()],
});
```

`sigxServer()` options: `include` (default `**/*.server.{ts,tsx,mts,js,mjs}`), `exclude`,
`base` (default `/_sigx/fn`), `serverApp` (a root-relative path to your
[`createServerApp`](/server/packages/server/usage#the-app) module), and the full
endpoint posture — `origin`, `maxBodyBytes`, `maxUrlBytes`, `maxResponseBytes`,
`timeoutMs` and `onError` — so dev runs the same knobs described below.

```js
sigxServer({ serverApp: '/src/server-app.ts' })
```

Dev loads that module eagerly through the SSR module runner and re-evaluates it
after edits, so the app-wide pipeline is live in development rather than
production-only. Production builds inject one side-effect import at the top of
`virtual:sigx-server-fns`.

`virtual:sigx-server-fns` is server-only: importing it from client code, or from
a `role: 'client'` build, is a build error. Two functions minting the same key
across files is a build error too.

The endpoint-level `guard` option is gone. App `middleware` runs at the same
pre-decode slot **and** reaches in-process SSR calls, which the wire-only `guard`
never could; a genuinely wire-only concern is one line in the middleware body:

```ts
if (fn.transport !== 'wire') return;
```

### Dev HMR — what refreshes in place

Function bodies are live in `vite dev` by construction — every call resolves its
module through the SSR module runner, so the next call after a save runs the new
body without a restart. An open page follows too:

| You save… | An open page that reads it with `useData(fn)` | An open page that does not |
|---|---|---|
| a `*.server.ts` module, or an inline `serverFn` carrier | refetches the affected `useData` cells in place — no reload, client state kept. The stubs the page already holds send the **new** version tag, so nothing 409s | reloads, unless it never loaded the stub |
| a server-only module they import (`db.ts` behind `api.server.ts`) | the same — the edit is routed to the stubs behind it | reloads |
| a server-only module a **rendered** component imports too | reloads — the document may have changed | reloads |

Pages that hold no stub for the edited source — a zero-JS resume route, another
tab — reload as before. The limits are deliberate:

- Server-rendered HTML that used a function with no live reader on the page
  (static islands content, an in-process call in the SSR entry) stays until a
  reload.
- An edit to the `serverApp` module — middleware, authentication — keeps the
  full reload.
- Module-level state in a server module (`let votes = 3`) resets when the module
  re-evaluates, exactly as a restart would.

For plugin authors: `serverFnHotUpdate(hot, keys)` from `@sigx/vite/hmr` is the
step each dev stub module runs when Vite re-evaluates it — it sweeps the SSR data
blob, refreshes every mounted cell on those keys (through `@sigx/cache` when it is
installed), and hands the update back to Vite when nothing on the page reads the
keys live.

## Production (Node)

The SSR build emits a registry chunk (`dist/server/sigx-server-fns.js`) that
maps every key to a `{ version, load }` record. Pass it **explicitly** to
`createServerFnHandler` from `@sigx/server/node` and mount the handler **before**
your document/SSR handler:

```js
import { createServerFnHandler } from '@sigx/server/node';
import { createRequestHandler } from '@sigx/server-renderer';

const { serverFns } = await import('./dist/server/sigx-server-fns.js');

app.use(createServerFnHandler({
  functions: serverFns,     // the build's registry chunk — never ambient
}));
app.use(createRequestHandler({ /* your document handler, unchanged */ }));
```

`createServerFnHandler` returns a connect-style `(req, res, next?)` middleware,
so it drops into Express/Connect/Polka and most Node servers.

## Edge (WinterCG)

For fetch-shaped runtimes (Workers, Deno, etc.), use `@sigx/server/server`.
Match the endpoint and hand the request off; anything else falls through to
[`createFetchHandler`](/server/packages/server-renderer/fetch-handler) — the
production document renderer for every fetch-shaped platform:

```js
import { createFetchHandler } from '@sigx/server-renderer/server';
import { handleServerFnRequest, matchesServerFn } from '@sigx/server/server';
import { serverFns, serverFnBase } from 'virtual:sigx-server-fns';

const handler = createFetchHandler({ template, app: (url) => createApp(url) });

export default {
  async fetch(request) {
    if (matchesServerFn(request, serverFnBase)) {
      return handleServerFnRequest(request, { functions: serverFns, base: serverFnBase });
    }
    return handler(request);
  },
};
```

`functions` is the build's registry, and it is how every entry learns its
functions — `handleServerFnRequest`, `createServerFnHandler` and
`app.serverFns()` alike. `serverFnBase` is the mount path the build baked in, so
`matchesServerFn`, the handler and `sigxServer({ base })` cannot disagree.

This composition — static assets → server functions → document render — is
exactly what the [deploy adapters](/deploy/docs/overview) scaffold as your
platform entry on Cloudflare, Vercel and Netlify; security defaults are
unchanged by deployment.

## Security defaults

Every server function is a public HTTP endpoint, so the runtime hardens each one
by default. You get all of this without opting in:

- **POST-only, JSON required.** Calls must be `POST` with a JSON content type.
  Because that content type is not
  [CORS-safelisted](https://fetch.spec.whatwg.org/#cors-safelisted-request-header),
  a cross-site form can't forge one — this is the CSRF gate. The endpoint never
  emits CORS headers.
- **Origin check** — default `'same-origin'`: the `Origin` header must match the
  request's origin.
- **A fail-closed pipeline** — middleware, then authentication, then the identity
  gate, all *before* the wire payload is revived. A function that declares neither
  `authorize:` nor `allowAnonymous: true`, under no configured app, denies with
  `401` rather than running open. An anonymous attacker's payload never reaches
  the codec or the validator.
- **Body & URL limits** — bodies are capped at `maxBodyBytes` (default 1 MiB)
  during the read; GET reads are capped at `maxUrlBytes` (default 8 KiB → `414`).
- **An immutable control seam** — the app config carrying `middleware`,
  `authenticate`, `authorize`, posture and `codec` is frozen when it is stamped,
  so nothing can weaken the pipeline in place at runtime. Reconfiguring means
  stamping a new app, which is an act with an owner rather than a silent
  assignment. See
  [the frozen config](/server/packages/server/api#the-config-is-frozen-once-stamped).
- **Prototype-pollution-safe parsing** on both the client and server sides.
- **Production error masking** — any non-`ServerFnError` throw becomes a generic
  `500`; the original never leaves the server.
- **Version skew is a `409`, never a wrong call** — a stale page's call carries
  its build's version tag, and a mismatch against the registry is refused with
  `code: 'version-skew'` before the pipeline runs. A `404` means only "unknown
  function".

### Request-handler options

`handleServerFnRequest` (edge) and `createServerFnHandler` (Node) take the same
`ServerFnRequestOptions`:

| Option | Default | Purpose |
|---|---|---|
| `functions` | — | The build's registry — `serverFns` from `virtual:sigx-server-fns`, key `<id>/<name>` → `{ version, load }`. Passed explicitly, never ambient. **Exactly one** of `functions` / `resolve`; both or neither throws when the handler is built. |
| `resolve` | — | The escape hatch: key → wrapped function, for a hand-built table. Return null/undefined for an unknown key (a structured 404). No version is known through this path, so it is never skew-checked. A **throwing** `resolve` is masked like any other failure — it does not leak. |
| `base` | `/_sigx/fn` | The mount prefix. Everything after it *is* the key, so pass the same value you gave `sigxServer({ base })` — `serverFnBase` from `virtual:sigx-server-fns` is the single source of truth. Overlapping mounts throw at mount time. |
| `origin` | `'same-origin'` | `'verify-when-present'`, an allowlist, or `false`. |
| `maxBodyBytes` | 1 MiB | Body cap, enforced while reading. An error **mid-read** is a `400`, not a 500 — a truncated upload is the caller's problem. |
| `maxUrlBytes` | 8 KiB | Cap on a GET read's query string → `414`. Sits under mainstream proxies' request-line caps. |
| `maxResponseBytes` | none | Opt-in **outbound** cap — the missing analog of `maxBodyBytes`, for a function whose result is unbounded (an unfiltered query, a runaway generator). Measures actual UTF-8 bytes, never `.length`. A breach is a masked 500 through `onError`. |
| `onError` | — | Observability seam for **masked** failures. |
| `timeoutMs` | none | Upper bound on the middleware + handler. Note the timeout race never triggers request-value disposal — a 504 does not yank resources from a still-settling handler. |
| `renderBoundaries` | — | Single-flight boundary refresh; `createBoundaryRefresh` from [`@sigx/resume/server`](/server/packages/resume/api) builds one. **Required for boundary refresh to happen at all** — omitting it fails silently. |
| `authorizeBoundary` | — | Vetoes ONE boundary descriptor under the request's principal, after the deps ∩ `invalidates` gate. Strict-`true`; a deny drops that descriptor silently, a throw drops the whole refresh. The mutation is never affected. |

Every posture option above is also settable once on
[`createServerApp`](/server/packages/server/usage#the-app) and inherited by every
mount and by bare `handleServerFnRequest` calls; an explicit per-call value wins.

The registry is a **null-prototype** object, so a key named `__proto__` or
`constructor` cannot reach anything but a real registration.

#### `onError`

Called for every **masked** failure — any non-`ServerFnError` throw from
middleware, a policy, `resolve` or the handler, timeouts included — in dev *and*
production, **before** the client response is built:

```ts
handleServerFnRequest(request, {
  functions: serverFns,
  onError(error, info, rq) {
    telemetry.report(error, { fn: info.name, url: rq.url.pathname });
  },
});
```

`ServerFnError`s are expected, client-visible failures and do **not** fire it —
this hook is for the errors the client never sees.

It is **awaited**, because an edge runtime may cancel post-response microtasks
and lose fire-and-forget telemetry. Its own throws are swallowed and never affect
the response.

#### `timeoutMs`

An upper bound on the middleware pipeline + handler, in milliseconds:

```ts
handleServerFnRequest(request, { functions: serverFns, timeoutMs: 10_000 });
```

On expiry the caller gets a `504`, `rq.abortSignal` fires — alongside client
disconnect, via `AbortSignal.any` — and `onError` receives the timeout error. So
a handler that threads `rq.abortSignal` into its own `fetch` and database calls
gets those cancelled too; one that ignores it keeps running.

For a stream, the bound covers **time to first chunk** only. Once an NDJSON
stream has started it is not bounded — cancel a long stream from the consumer
side instead.

There is no default: without `timeoutMs`, a handler runs until it settles.

> **Everything here is app-wide, not per-transport.** Configure the posture once
> on [`createServerApp`](/server/packages/server/usage#the-app) and every mount
> inherits it, in-process SSR calls included — there is no longer a wire-only
> layer to keep in sync with a definition-level one. Per-operation authorization
> stays on the function, as
> [`authorize:`](/server/packages/server/usage#writing-a-policy).

### Relaxing a default — deliberately

A few options weaken a default on purpose. Reach for them only when you mean to:

- **`cache` (a GET read)** drops the JSON content-type CSRF gate — only mark a
  function `cache` when it is genuinely side-effect-free.
- **`form: true`** gives up the JSON-CSRF layer so the function can accept a
  progressively-enhanced HTML form post; the origin check stays at full strength,
  and `input` is required.
- **`public: true`** on a read is a promise that its output depends only on its
  arguments — no cookies, auth or per-user headers.
- **`origin`** can be widened from `'same-origin'` to `'verify-when-present'` (to
  admit Origin-less programmatic clients), an explicit allowlist, or `false` for
  a deliberately public API.
