# Server Functions

`@sigx/server` is how a SignalX app talks to its own server. You write an async
function, mark it as a server function, and call it from a component like any
other `async` function — the framework turns it into a typed RPC endpoint, runs
the body on the server, and returns the result. No REST routes to design, no
fetch wrappers to hand-write, no request/response DTOs to keep in sync.

> **Not the same as `@sigx/server-renderer`.** The
> [server renderer](/server/packages/server-renderer/overview) turns your
> component tree into HTML on the server. `@sigx/server` is the RPC layer — the
> way running components read and write server-side data. They compose, but you
> can use either on its own.

> **Need identity, ordering or memory between calls?** A server function is
> stateless by design. [`@sigx/actors`](/actors/) builds on this package —
> an actor call *is* a synthesized server function, inheriting these guards, this
> codec and this origin policy — and adds an addressable object that handles one
> call at a time and keeps its state.
> [Which to use](/actors/docs/actors-or-server-functions) is a short read.

```ts
// src/cart.server.ts — a server-only module
import { serverFn, requirePrincipal } from '@sigx/server';
import * as z from 'zod';
import { db } from './db';

export const addToCart = serverFn({
  input: z.object({ productId: z.string(), qty: z.number().int().positive() }),
  handler: async ({ input: { productId, qty }, rq }) => {
    const user = await requirePrincipal<User>(rq);   // resolved by the app's authenticate
    return db.cart.add(user.id, productId, qty);
  },
});
```

```tsx
// any component — addToCart is just an async function here
import { useAction } from 'sigx';
import { addToCart } from './cart.server';

const add = useAction(addToCart, { cache: { invalidates: [['cart']] } });
// add.run({ productId: 'sku-1', qty: 1 }) → POSTs to the server, runs the handler, returns the row
```

The `db` import never reaches the browser: the client build replaces
`*.server.ts` with typed fetch stubs, so the bundle ships only the call
signature. The server keeps the real module. And there is no hand-rolled session
check: the runtime is fail-closed, so an anonymous caller was refused with a 401
before the handler ran, and `requirePrincipal` is the typed accessor for the
identity the app's `authenticate` resolved.

## What you get

- **Plain-function ergonomics.** A server function is called with its declared
  input and returns its declared type. Input and return types flow from the
  definition to the call site, and the input is validated on the server by the
  schema that types it.
- **Value-first data flow.** Server functions are the natural fetchers for
  [`useData`](/core/docs/data-loading) (reads) and `useAction` (writes), so
  loading, error and refresh state come for free.
- **Secure by default.** Every server function is a public HTTP endpoint, and
  the runtime treats it as one: POST-only with a required JSON content type (a
  CSRF gate), a same-origin check, body-size limits, prod error masking and an
  app-wide guard hook. See [Deployment & security](/server/packages/server/deployment).
- **Streaming.** `serverStream` yields values over time (NDJSON on the wire) and
  plugs a string stream straight into `useStream` for token-at-a-time output.

## Requirements

This section documents `@sigx/server` **1.0**, where `serverFn({ input?, handler })`
is the one authoring form. Install the package:

```bash
npm install @sigx/server
```

`@sigx/server` depends on `sigx` and `@sigx/serialize` (pulled in
automatically). During development the endpoint is served with zero config by
the `sigxServer()` Vite plugin from `@sigx/vite/server`; see
[Deployment & security](/server/packages/server/deployment) for the dev, production (Node)
and edge (WinterCG) wiring.

## The model in one paragraph

Each server function has one stable key, `<id>/<name>`, and is served at
`POST /_sigx/fn/<id>/<name>`. Calling the stub sends `{"args":[input],"v":"<version>"}`
as JSON — `v` is the build's version tag for the function — and the server
validates and runs the function and replies with `{"data":...}` or a structured
`{"error":{ message, status, code?, data? }}`. A stale page after a deploy gets a
`409` version-skew error rather than a wrong call. The input crosses the wire as a
**typed value** — there is no closure serialization, so a server function can
only see what you pass it, its imports, and server-side globals. That single
constraint is what makes the boundary safe and the types honest.
