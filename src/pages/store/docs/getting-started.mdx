# Getting Started with Store

`@sigx/store` provides centralized, reactive state built on the same signal core that powers your components. You define a store once with `defineStore`, describe its state, actions, and derived values inside a setup function, and then call the returned factory anywhere to get a live, reactive instance.

The store surface is **flat and signal-first**: whatever your setup returns becomes the store. Returned state keys read and write as plain values (`store.count`), returned computeds read as plain read-only values (`store.total`), and actions are called directly (`store.increment()`). Reading any of them inside a component's render function makes that component re-render automatically when the value changes — no selector layer, no manual subscriptions.

## Why a store?

- **Centralized state** shared across components instead of prop-drilling.
- **Signal-backed reactivity** so reads in render functions update automatically.
- **A flat, fully-typed surface** — public state is exactly the signals you return.
- **Actions** with a reactive `pending` flag and lifecycle events (`onDispatching`, `onDispatched`, `onFailure`) riding on each action function.
- **Per-key change events** (`store.$events.count`) that cost nothing until someone subscribes.
- **Atomic multi-key updates** via `patch` / `$patch` (one reactivity flush).
- **Real lifetimes** (`'singleton' | 'scoped' | 'transient'`) and automatic cleanup — a store created inside a component disposes on unmount.
- **Built-in persistence** at the `@sigx/store/persist` subpath.

## Your first store

Define a store with `defineStore(name, setup)`. The `setup` function receives a context object that includes `defineState` and `defineActions`. Whatever you return becomes the store's surface — spread the `signals` from `defineState` to make those keys public state.

```tsx preview code live
import { component, render } from 'sigx';
import { defineStore } from '@sigx/store';

const useCounterStore = defineStore('counter', ({ defineState, defineActions }) => {
    const { state, signals } = defineState({ count: 0 });

    const actions = defineActions({
        increment() { state.count++; },
        decrement() { state.count--; },
        reset() { state.count = 0; },
    });

    return { ...signals, ...actions };
});

const Counter = component(() => {
    const store = useCounterStore();

    return () => (
        <div class="flex items-center gap-3">
            <button class="btn" onClick={() => store.decrement()}>-</button>
            <span class="text-xl font-bold w-12 text-center">{store.count}</span>
            <button class="btn" onClick={() => store.increment()}>+</button>
            <button class="btn btn-ghost" onClick={() => store.reset()}>reset</button>
        </div>
    );
});

render(<Counter />, "#sandbox");
```

## How it fits together

- `defineStore(name, setup, lifetime?)` returns a **factory function**. By convention it is assigned to a `useXxxStore` const, but it is an ordinary function — calling it creates (or resolves) an instance. There is no `useStore` export.
- Inside `setup`, `defineState(obj)` returns `{ state, signals, events, patch }`. `state` is the deep reactive object you mutate inside the setup and actions; `signals` are spreadable per-key views — **the keys you return become the store's public state**, unreturned keys stay private.
- `defineActions(obj)` wraps your functions. Each returned action is callable with its original signature and carries a reactive `pending` flag plus `onDispatching` / `onDispatched` / `onFailure` event subscribers.
- The store instance is an **unwrap proxy**: returned key signals read/write as plain values, returned `computed(...)` values read as plain read-only values, everything else passes through.
- Store meta lives behind `$`: `$id`, `$patch`, `$events`, `$dispose`.
- Calling the factory inside a `component(...)` setup ties the instance to the component lifecycle: it auto-disposes on unmount.

## Reading and writing state

On the instance, returned state keys are plain values — read them and assign to them directly. Inside the setup, mutate `state` (it is deeply reactive) or use `patch` for an atomic multi-key update.

```ts
const store = useCounterStore();

store.count;          // read (reactive when read in a render/effect)
store.count = 5;      // write — same as setting state.count inside the setup

store.$patch({ count: 0 });           // atomic multi-key update (object form)
store.$patch(s => { s.count += 2; }); // ...or mutator form

store.$events.count.subscribe((value, prev) => {
    console.log('count went from', prev, 'to', value);
});
```

Per-key events are **lazy**: the deep watcher behind `$events.count` only runs while someone is subscribed, and it does not fire immediately on subscribe.

> One convention to internalize early: **don't destructure the store**. `const { count } = store` snapshots the current value and loses reactivity. Either keep reads on the store (`store.count`) or use [`storeToSignals`](/store/docs/using-in-components#destructuring-safely-with-storetosignals) for destructuring-safe signal views.
